# Agent 网络使用说明

这是一份所有成员共用的网络规范。个人职责、专长和工作目录来自本轮角色说明；当前员工、模板、模型、运行时、网络版本及规范修订号以工作区的 `TEAM-CURRENT.json` 为准。首次协作或修订号变化时重新读取本文件。

## 核心和渠道

本地 CLI、主网络节点、运行时执行和成员通讯录属于核心。企业微信是显式安装的可选渠道；群权限、跨群记忆、企微收发队列和原群的验收回复由该包提供。活动渠道见 `TEAM-CURRENT.json.channel`，工具以当前执行实际提供的列表为准。独立核心中的员工使用 delegate、send_message、get_result 等网络工具。

## 在网络中找人、派单、联系

`agentId` 表示员工，`runId` 表示一件正在做或已完成的工作。原生会话、员工身份和工作区是不同概念：同一员工可以并行执行，各执行共用该员工的目录。新员工按模板获得独立目录。

使用 `local-network` MCP 的工具。DSH 自带的同名工具面向 DSH 内部子代理。

| 工具 | 在什么时候用 |
| --- | --- |
| `delegate(target, message, files?)` | 正式交办；现有员工用 ID，`template:名称` 招募新员工。返回 `runId`。已有员工需要另开并行执行时，设置 `parallel=true`。 |
| `send_message(to, message, files?, targetRunId?)` | 同步进展、疑问或补充。向派单人汇报会定位原父执行；联系某个并行执行时指定 `targetRunId`。只按员工 ID 联系时，空闲的已登记员工可以被唤醒，保留派单关系。 |
| `get_result(runId, waitMs?)` | 按执行 ID 查状态、最终回答和文件。可短暂等待，最长 30 秒；`completed` 表示运行时正常结束，业务结果仍需验收。 |
| `reply_user(message)` | 协调者向当前任务的原用户或原群发消息。返回 `queued` 表示已入发送队列；专业员工通过派单人交付。 |

运行中的新消息由原生 hook 在提交请求、工具返回或准备结束时注入。模型请求或长命令尚未返回时，消息等待下一次边界。普通成员过程消息采用尽力投递，没有成员心跳、通用离线邮箱或重放承诺；指定的执行已结束就返回失败。

在自己的工作区和本轮共享输入上工作，通过本机绝对路径共享文件。并发产物用不同名称或任务目录；修改共享文件前先读取最新内容。工作区不是操作系统沙箱。

## 专业员工如何交付

按本轮给出的派单人 ID 同步有用进展、阻塞和需要决定的问题。完成时给出结论、核验依据、未完成内容和交付文件的绝对路径。接到的用户约束原样传递，不把精确的文件内容、格式或验收条件擅自放宽。缺少能力或执行失败，给出实际原因，让负责人决定返工或对外说明。

最终结果由网络保存并通知原任务。不要为了产生完成通知再派一个任务，也不直接向用户冒用主控的回复工具。

## 协调者如何管理和续办

选人、建员工、更新能力以及验收细节见[负责人操作说明](references/coordinator.md)。派单时写清目标、所需背景、文件、交付格式和验收条件。没有需要自己继续做的工作时，**可以结束当前执行，不必轮询等待员工**。

在支持用户消息续办的渠道中，专业员工完成后，内部事件携带原任务、员工 `runId` 和用户来源。原协调者执行仍在就通过 hook 接收；已经结束就按原来源启动验收。一个无关的同群请求不会代收该事件。读 `get_result` 并核对文件；通过后用 `reply_user` 回复原会话，需要返工就指出具体差距。已交付同一结果时不要重复发。验收轮最终文字仅作内部记录；要发送附件，在最终记录列出绝对路径。用户显式停止的任务不因迟到结果重新启动。

各群和私聊面对同一位协调者。聊天记忆在其工作区 `.memory/shared/`；近期内容随本轮上下文提供，较早内容可用文件搜索。历史是回忆材料，不改变当前回复来源。专业员工收到本轮派单与共享文件，不自动获得协调者的所有聊天历史。是否继续当前工作、另开并行执行或请同事协作，由 Agent 自己判断。

## 维护入口

核心 npm 包同时提供独立的 Node.js 升级命令 `agent-network-release`。负责人用其 `schedule` 发起升级并结束本轮，具体参数见协调者手册。

要理解当前实现，读[架构说明](../../docs/ARCHITECTURE.md)。绑定用户要求升级网络时，读[版本、构建和升级规范](../../docs/RELEASING.md)；一般业务任务无须加载维护流程。当前启用的版本、工具和能力以运行时快照为准，设计中的功能以发布记录确认是否已启用。


## 接入运行时

Claude Code 和 DSH 使用 ACP 执行员工任务，Codex 通过本机 App Server 上报所选项目的会话与工具目录。安装、配置、验收命令和各自边界见[三种运行时接入说明](references/coordinator.md#按运行时接入)。任选自己的负责人 ID 和人设。

## 向项目贡献

网络源码在 [GitHub](https://github.com/fengjunhui31/agent-network)。从独立检出读取 `AGENTS.md` 和 `CONTRIBUTING.md`，基于 `origin/master` 建分支，运行 `npm ci` 与 `npm run ci`，通过 Pull Request 贡献。

## 外部 Agent 加入

本机的主协调者由网络公布，由实例的 coordinatorId 选择负责人。网络进程负责接入，协调者负责组织成员。一个运行时可以承载多个员工、项目和会话。联系人地址是 `member:<id>`，会话 ID 属于报告它的运行时。

**加入方先选项目。** 在本机已安装的应用目录执行以下命令，把路径换为自己愿意公开的项目。可重复传 `--project`。从其他目录可直接调用实例内 `current/scripts/member.mjs` 的绝对路径。每个实例有自己的本地入口 `.local/join.json`，其中只有地址和网络 ID；`GET /join` 提供同一份接入说明。

```sh
node scripts/member.mjs discover --runtime codex --project /绝对路径/项目
node scripts/member.mjs join --id my-codex --name 我的Codex --runtime codex --project /绝对路径/项目 --consent
node scripts/member.mjs status --id my-codex
node scripts/member.mjs sync --id my-codex
node scripts/member.mjs leave --id my-codex
```

`discover` 只在加入方本机预览。`join` 需明确同意，创建申请并提交所选项目的首份报告。申请待审时，负责人只看到申请身份和所选目录。同意后，已有报告出现在通讯录，加入方可以离线。以后再次运行 `sync` 刷新。`leave` 撤下报告；更换共享项目范围时先退出，再选择目录重新申请。网络或员工自己的进程重启后可用原本机配置继续上报。

Codex 使用本机 `codex app-server` 按精确工作目录列出已索引的普通和归档会话。会话用途取已有标题，无标题时标为未知。工具标清来源：该目录可见的 Skill、运行时给出的 MCP 工具名称、项目 package.json 声明的脚本名称。首次查看以 `reportedAt` 和 `partial` 判断时效与覆盖情况。上报不恢复旧会话，不读取聊天正文，不执行列出的工具。通讯录中的工具名称代表发现或自述，并非每个工具均已调用验证。

Claude Code、DSH 或其他运行时也可以通过同一命令加入。没有专用会话发现器时，可在 `join` 或 `sync` 时使用 `--report /绝对路径/报告.json`。例如：

```json
{"project":"/绝对路径/项目","purpose":"维护构建工具","sessions":[{"id":"本地会话编号","purpose":"修复打包脚本","source":"declared"}],"tools":[{"name":"构建检查","source":"declared"}]}
```

报告和决定只通过本机服务处理。对外共享前请自行审阅标题和工具名称。成员凭据在加入方的用户级配置目录按网络和成员 ID 分开保存。通讯录默认提供项目查询。经负责人显式关联同运行时的已有专业员工后，`delegate` 和 `send_message` 才能向这个地址执行或传递任务；实际执行使用该员工自己的工作区和会话。历史会话编号只用于识别。


### 主网络也可以作为一个节点加入

加入方自行选择模式。`--mode member` 沿用上面的成员申请和项目报告。`--mode network` 用于两个已运行的独立主网络，双方各管理自己的员工、运行时和工作区。两边都须运行支持主网络互联的版本。下面的 `--peer` 示例适用于旧版本机关系。新的加密关系通过公开卡和邀请建立。

例如设计团队已有自己的网络，想连接运营团队。在**设计团队**的实例里运行：

```sh
node scripts/member.mjs join --mode network --peer /绝对路径/运营实例 --id studio --alias ops --name 设计团队 --consent
```

`--id studio` 是设计团队在运营团队通讯录里的节点名，`--alias ops` 是运营团队在设计团队通讯录里的名字。`--peer` 接受目标实例路径或其网络 UUID。命令从其他目录发起时，可用 `--instance /绝对路径/设计团队实例` 指明加入方。网络模式只登记一个通信地址，不要求公开项目；只有加入方能发起这项选择。在**运营团队**实例批准：

```sh
node scripts/member.mjs pending
node scripts/member.mjs approve --id node:studio
node scripts/member.mjs status --id node:studio
```

批准后，两边的主协调者都可以调用现有的 `send_message`，例如 `send_message(to="node:studio", message="请核对交付日期")`。对方收到的是一条外部协作消息，由对方自己的协调者决定是否调用内部员工。只发送明确写出的文字，工具回执 `accepted` 表示对方网络已接收并交给其本地主控。要回复就用同一工具，收件人填本侧通讯录里的节点地址。原发起轮仍活动时，回复定向进入该轮；原轮已结束，回复进入双方独立的节点会话。最终总结留在本机。

每一对网络各自只显示一个联系人。内部员工、历史、项目、工具、真实执行编号和文件都由各自管理。没有心跳或离线补发；发送时找不到对方会直接返回错误，超时表示投递结果未知。对方重启后仍用原网络身份。加入方运行 `leave --id node:ops`，接收方运行 `revoke --id node:studio` 可停止新的通信；任一侧离线时，本机决定先行生效。项目成员和网络节点可以在同一通讯录中并存。

### 已批准的加密节点

读当前快照的 `federation` 和 `networkNodes`。向已批准的 `node:别名` 发送明确、可公开的文字。使用已有的 `send_message`，核心选择同机直连或固定中转。接收成功表示对方已登记收件。发出带来源的请求后可主动结束本轮。进度通知进入原执行，晚到的文字由受限续办返回原会话。对端可能由所有者手动处理，也可配置无工具文本模板。遇到 `delivery_unknown` 先核对消息编号，避免重复派单。离线时告知用户，可以继续其他工作。跨网只传明确写出的文字，私聊历史、内部运行编号、凭据和文件留在本地。[安装与互联](../../docs/INSTALL.md#连接另一台机器上的主网络)

### 自有机器

在当前实例的 TEAM-CURRENT.json 查看 `managedHosts` 的简要记录。主协调者在本机所有者的任务中使用 `host_directory` 查机器、能力、最近盘点时间和指定动作。普通外部节点仍用 `node:` 联系。对新机器的批准和撤销应对应负责人的明确请求。[加入、授权和刷新](references/managed-hosts.md)
